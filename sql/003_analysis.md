# Denormalization vs integration events

The Jobs module needs a customer display name on the office dashboard. Contacts owns that data. Copying `customer_name` onto `jobs.jobs` is denormalization; joining at read time keeps a single source of truth; syncing through `CustomerRenamedIntegrationEvent` is a third option.

Denormalize when the read path is hot and the foreign data is slow or unavailable. A dashboard that lists 50 jobs must not hop to the Contacts module (or worse, a synchronous HTTP call) for every row. Storing `customer_name` on the job at creation time makes the list query one index scan. The cost is staleness: if the customer marries and changes their name, every denormalized copy is wrong until something updates it. That is acceptable when the field is a snapshot ("who did we bill as on the day we scheduled") and the office can live with eventual correction.

Use integration events when another bounded context must react, not merely display. Completing a job is the textbook case: Billing must create an invoice and Notifications must email the customer. Jobs does not reference Billing types. It writes `JobCompletedIntegrationEvent` into the outbox in the same transaction as the status change. Hangfire later dispatches the event. Billing upserts an invoice keyed by `JobId + CompletedAt`, so at-least-once delivery cannot double-charge. Contacts would similarly subscribe to `CustomerRenamedIntegrationEvent` if we had denormalized the name and needed to refresh it.

Consistency trade-offs are explicit. A join against Contacts (same database, different schema) is immediately consistent but couples deployability and runtime availability: if Contacts is down or its schema moves, Jobs reads break. Denormalization plus events is eventually consistent: the dashboard is fast and Jobs stays up, but there is a window where the name on the job is stale. Outbox + unique idempotency key makes that window short and safe. We chose owned Address columns (same aggregate, same transaction — not a cross-context join) and event-driven Billing (different module, different schema) because those match the consistency needs of each relationship.
